# ADR-003: OCR engine and reading order

- **Status:** **Proposed.** The code uses Tesseract by default. That is Claude's default, **not yet a decision by the owner.**
- **Date:** 2026-11-11

## Question

Which OCR approach should read scanned newspaper pages?

## Options

| Option | Gain | Cost and risk |
|---|---|---|
| **Tesseract (local) plus a column-aware reading order** (current default) | Free, offline, small, easy to run in Docker, no data leaves the machine | Newspaper layout is its weak spot; quality depends heavily on scan quality; the column fix is my own heuristic |
| Layout-aware ML OCR (for example PaddleOCR or docTR) | Better on complex layouts | Large install, much more RAM, slower on CPU; competes with the observability stack for memory |
| Cloud OCR (for example AWS Textract) | Strong on documents and tables, no local compute | Costs money per page, needs credentials and network, uploaded pages leave the machine; this is a good production option but not a local-first one |

The OCR sits behind a small interface (`OCREngine` in `ingest/ocr.py`), so changing the engine touches one file.

## What was measured (honest evidence)

All tests used a **synthetic** two-column newspaper page generated by a script, not real scans.

- Plain Tesseract, any page-segmentation mode (1, 3 or 4): the two columns were **interleaved line by line**, and
  some words were lost.
- With the column-aware reading order in `ingest/layout.py` (find the empty vertical gutter from word boxes, read
  column by column, headline first):

| Variant of the synthetic page | Mean confidence | Left column read before right |
|---|---|---|
| clean | 95.7 | yes |
| skewed 1.5 degrees | 95.7 | yes |
| skewed 3 degrees | 94.6 | **no** (falls back to the scrambled order) |
| added noise and blur | 95.9 | yes |
| half resolution | 95.9 | yes |

Reading it correctly: the heuristic works when columns are separated by a clean vertical strip. A real
photographed newspaper has skew, curl, shadows, ads, photos, captions and ragged column breaks. **I have no
evidence yet about real pages.** The 3 degree failure shows how fragile the rule is.

The heuristic falls back to Tesseract's own order when it finds no clear gutter, so it should not make plain
cases worse, but that is only checked on synthetic data.

## Recommendation (for the owner to accept or change)

1. Keep Tesseract for now.
2. Build the **OCR evaluation harness** (milestone M2): 10 to 20 of the owner's real scans, each with a
   hand-typed reference text, scored on character error rate and on whether paragraphs come out in reading order.
3. Add **deskewing** if the harness shows skew is the common failure.
4. Decide between staying, a layout model or a cloud engine **using those numbers**, then update this ADR.

## Decision

_Pending: the owner._

## Consequences

Until this is decided, reports on multi-column pages may contain scrambled text, and the signals computed from
that text are less meaningful. The OCR confidence signal does **not** catch this: a scrambled page can still have
high word confidence.
